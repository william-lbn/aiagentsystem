## 问题背景与学习目标

MCP 连接工具，A2A 连接 Agent。多 Agent 系统需要能力发现、任务状态、消息上下文、取消和 artifact 协议。

## 核心概念与系统直觉

本节不把概念当作术语清单，而是回答三个工程问题：它**是什么**、在系统里**负责什么**、以及它失效时**会留下什么可观测证据**。

### Agent card

**定义。** 对外声明 Agent endpoint、能力、技能和交互元数据的发现对象；它描述“能声称做什么”，不是信任证明。

**系统责任。** Card 帮助 peer 发现和协商能力，但调用方仍需独立认证、授权、版本兼容和业务能力验证。

**失败边界。** 把公开 card 当成身份或安全凭证会让恶意服务自称高权限 Agent；能力描述过期也会导致错误路由。

### Task

**定义。** A2A 中具有生命周期、状态、owner 和可能长时执行语义的工作单元。

**系统责任。** Task 为异步执行、取消、订阅和结果关联提供稳定 identity，比单次消息更适合长时协作。

**失败边界。** 若 task identity 与实际 effect 不绑定，重试可能创建两个远端任务；取消请求也不代表远端 effect 已撤销。

### Message

**定义。** Agent 与 Agent 之间交换的指令、上下文和反馈载体，属于协作语义而不是 durable truth 本身。

**系统责任。** Message 应携带明确 role/part/content 和 correlation，并避免把大对象或秘密无边界复制到所有 peer。

**失败边界。** 自然语言 message 容易产生语义漂移与 prompt injection；仅保存消息无法证明远端系统实际完成了什么。

### Artifact

**定义。** Task 产生的结构化交付物，如文件、数据、报告或机器可消费结果，应带版本、媒体类型和 provenance。

**系统责任。** Artifact 把协作从“聊天结束”提升为“交付物可验证”，并可被下游 verifier 或另一个 Agent 消费。

**失败边界。** 没有 provenance/hash 的 artifact 可能与 task 状态不一致；把 artifact URL 当成可信内容也可能引入供应链风险。

## 原理与理论基础

### 系统不变量

> **Invariant**：agent discovery metadata and task state are untrusted protocol inputs and require validation

不变量与普通“最佳实践”不同：最佳实践可以因为场景变化而替换，不变量一旦被破坏，系统就失去本章希望保证的正确性。例如 `把 agent-to-agent 做成普通 chat` 并不是一个 UI 问题，而是说明某个状态已经无法从证据中唯一判断。


### 故障模型

本章优先把 “把 agent-to-agent 做成普通 chat”、“没有 task id 无法恢复”、“上下文跨 agent 泄漏” 作为可证伪故障，而不是泛化地枚举所有异常。对涉及外部 effect 的失败，判定顺序固定为“最后 durable state → effect 是否可能发生 → 现有 observation 是否足够决定下一步”；证据不足时停在 UNKNOWN/显式失败。

### Why / What if / Trade-off

本章真正的设计取舍不是“使用更强模型还是写更多规则”，而是确定 **Agent card** 与 **Task** 分别应该由概率性决策还是确定性软件拥有。模型可以帮助识别候选路径，但它不会自动消除“把 agent-to-agent 做成普通 chat”这类系统失败；该失败必须由 runtime 的 schema、状态机、权限或 verifier 显式约束。

如果把 Agent card 完全交给模型，系统会把不可验证的语言判断混入执行事实；如果把 Task 全部硬编码为固定 workflow，又会失去开放任务所需的适应性。更稳健的边界是：让模型负责提出候选决策，让软件负责 `能力声明机器可读`、`cancel 语义明确` 以及对不变量 **agent discovery metadata and task state are untrusted protocol inputs and require validation** 的检查。

**What if。** 一旦“没有 task id 无法恢复”发生，系统首先需要判断现有证据是否足够决定下一状态；证据不足时应停在显式失败或待协调状态，而不是让模型用自然语言补全事实。这个边界决定了本章方案是否具有可恢复性，而不只是演示效果。


### 形式化模型与可证伪假设

$$
Delegation=(Principal,Agent,Task,Scope,Expiry,Trace)
$$

A2A 解决互操作，但跨 Agent 信任需要可验证 delegation：谁代表谁、能做什么、到何时为止、如何追踪。

**可证伪假设。** 将 delegation token 与 task/scope/expiry 绑定后，可以阻断“协议可达但无权执行”的横向扩权。

**建议测量。** delegation validation、scope violation、identity continuity、revocation latency。

**Step 3 — artifact 有类型和引用。** `artifact 有类型和引用` 是“A2A 与 Multi-Agent 互操作”的一次显式状态转移。输入和输出都必须可序列化并关联 `run_id/step_id`；一旦该步骤失败，后继步骤只能依据已记录状态继续。关键观察点是 `Message` 是否仍满足 **agent discovery metadata and task state are untrusted protocol inputs and require validation**。

**Step 4 — cancel 语义明确。** `cancel 语义明确` 是“A2A 与 Multi-Agent 互操作”的一次显式状态转移。输入和输出都必须可序列化并关联 `run_id/step_id`；一旦该步骤失败，后继步骤只能依据已记录状态继续。关键观察点是 `Artifact` 是否仍满足 **agent discovery metadata and task state are untrusted protocol inputs and require validation**。

在本章的 `Agent card` 场景中，**最后一步 — 验证。** verifier 针对 `Artifact` 检查本章不变量 **agent discovery metadata and task state are untrusted protocol inputs and require validation**。如果“把 agent-to-agent 做成普通 chat”使现有 artifact/外部状态不足以证明成功，结果必须停在显式失败或 UNKNOWN；只有 observation 能闭合状态转移时，流程才允许进入 FINISHED。

### 数据流与控制流

本章的数据/控制链按 **能力声明机器可读 → 任务状态可轮询 → artifact 有类型和引用 → cancel 语义明确** 推进。调试时不要只看最终 answer，应确认每一阶段的输入来源、状态版本和 observation；对“把 agent-to-agent 做成普通 chat”尤其要检查动作前后的证据是否足以闭合不变量 **agent discovery metadata and task state are untrusted protocol inputs and require validation**。


### 持久化点与崩溃窗口

本章需要持久化的内容取决于动作可逆性。与 `Agent card` 有关的纯计算状态通常可以重算；一旦 `任务状态可轮询` 可能产生昂贵、外部或不可逆效果，就必须在动作前后建立可区分的证据边界。对于本章不变量 **agent discovery metadata and task state are untrusted protocol inputs and require validation**，恢复时最重要的问题是：最后一个已知状态是什么、动作是否可能已经发生、现有 observation 能否唯一决定 retry/continue/compensate。

### 核心机制实现

```python
def a2a(fault=False):
    card = AgentCard(
        name="researcher",
        description="Evidence-oriented research agent",
        supported_interfaces=[AgentInterface("https://agent.invalid/a2a", "JSONRPC")],
        version="1.0.0",
        default_input_modes=["text/plain"],
        default_output_modes=["text/plain"],
        skills=[AgentSkill("search", "Search", "Search cited evidence", ["research"])],
        capabilities={},
    ).to_wire()
    task = A2ATask("t1", "ctx1", "TASK_STATE_WORKING").to_wire()
    if fault:
        task["status"]["state"] = "working"  # 非 v1 ProtoJSON enum spelling

    valid, errors = validate_a2a_1_0(card, task)
    condition = valid if not fault else (not valid and "task_state_invalid" in errors)
    return _ok("a2a", fault,
               {"card": card, "task": task, "valid": valid, "errors": errors},
               "A2A 1.0 AgentCard discovery metadata and TaskStatus state are untrusted protocol inputs and require validation",
               condition)
```


本地 helper 只实现课程所需的 A2A 1.0 wire-contract 子集，并明确拒绝把旧版/自定义 `endpoint + flat task.state` 当成 1.0 规范。AgentCard 通过 `supportedInterfaces[]` 声明 transport/interface，并提供结构化 `skills` 与默认 input/output modes；Task 的生命周期位于 `status.state`，状态值按 v1 ProtoJSON enum（如 `TASK_STATE_WORKING`、`TASK_STATE_COMPLETED`、`TASK_STATE_INPUT_REQUIRED`、`TASK_STATE_AUTH_REQUIRED`）校验。

官方实现证据使用 PyPI `a2a-sdk==1.1.2`（不要与源码仓库 v1.1.4 tag 混写）：客户端通过 `/.well-known/agent-card.json` 发现接口，再经 JSON-RPC 向独立服务进程提交采购风险审查。官方 `DefaultRequestHandler`、`InMemoryTaskStore`、`AgentExecutor` 与 `TaskUpdater` 实际产生 `Task(SUBMITTED) → WORKING → Artifact → COMPLETED` 流，客户端 artifact 与服务端 effect record 一致；旧版顶层 card 字段被 ProtoJSON 严格解析器拒绝。证据包见 [`a2a-sdk-conformance`](../../../evidence/l5/a2a-sdk-conformance/2026-09-12-macos-arm64-py313-v1.0.0/evidence.json)。


### 简化假设与不能省略的机制

风险决策器是确定性策略，不使用 LLM，这是为了让互操作失败不会被模型输出噪声掩盖。不能省略 Agent Card discovery、task/context identity、状态事件顺序和服务端 effect；只做 protobuf `MessageToDict` round-trip 只能证明 schema，不足以证明 client/server 互通。本实验仍限于 Python↔Python loopback JSON-RPC；跨语言、HTTP+JSON/gRPC parity、远程 auth、durable task store、cancel/subscribe 都是更高一层验收项。

- `fan-out width`
- `duplicate-work ratio`
- `handoff latency`
- `context isolation violations`
- `critical-path latency`
- `cost amplification`


### 优化顺序


任何优化都必须重新运行 Lab A/B。尤其当优化改变 `Task` 的生命周期时，要重新验证 **agent discovery metadata and task state are untrusted protocol inputs and require validation**；否则平均延迟下降可能以更大的 stale state、重复副作用或取消失效为代价。

### 可靠性工程

本章可靠性 gate 直接针对 “把 agent-to-agent 做成普通 chat”、“没有 task id 无法恢复”、“上下文跨 agent 泄漏”：只有正常路径与对应 fault path 都保持 **agent discovery metadata and task state are untrusted protocol inputs and require validation**，优化或功能扩展才可接受。是否达到 detection、containment 或 recovery 以实验的 `evidence_level` 字段为准。


## 技术边界与设计取舍
本章方案有明确边界：

- 增加 Agent 数量不会自动增加正确性，可能只增加通信与成本
- 共享记忆会引入污染和竞态，完全隔离又会损失协同
- 跨组织 A2A 不能默认信任 Agent Card、message 或 artifact
- 分布式协调仍受超时、重试、重复消息和部分失败影响

选择方案时要回到本章边界：如果业务不能接受“把 agent-to-agent 做成普通 chat”，就必须为 `Agent card` 增加更强的确定性约束；如果主要任务是开放式探索，则可以把更多 `Task` 决策交给模型，但要用 `cancel 语义明确` 保持结果可验证。**A2A Protocol** 与 **Google Agent Development Kit** 的差异也应放在这些约束下理解，而不是抽象成通用框架排名。

A2A 解决 Agent 间任务互操作，不自动解决跨 Agent 授权、信任或责任边界。AgentCard/Task 的 wire model 应按规范校验；跨组织调用还需要 identity、policy、provenance 与可撤销委托。

当前研究和工业演进已经从“模型能否调用工具”推进到“怎样让长期、状态化、具有副作用的 Agent 可评估、可恢复、可治理”。与本章直接相关的资料：

- **[Google Agent Development Kit](https://github.com/google/adk-python)**（v2.1.0 @ 6d15e19）：Agent、workflow、sandbox、telemetry、evaluation/deployment 参考实现。

**本章吸收的变化。** A2A 解决任务/消息/artifact 互操作，但互操作不等于身份与授权。跨 Agent 委托必须保留 principal、scope、expiry 与可追踪 task identity。这些研究/规范的价值不在于替换本章原理，而在于把上述假设放进更真实、更长时或更高风险的环境中检验。

### Research Gap

围绕 `Agent card`，当前缺口不是“再增加一个 Agent API”，而是怎样把 **agent discovery metadata and task state are untrusted protocol inputs and require validation** 从局部实现经验升级为跨模型、跨 runtime 可验证的系统属性。现有工业实现已经能够提供 tool loop、session、graph、plugin 或 workspace 等抽象，但在“把 agent-to-agent 做成普通 chat”和“没有 task id 无法恢复”同时出现时，证据格式、恢复语义和评测方法仍缺少统一答案。

本章的研究更新不追求论文数量，而关注一个问题：现有工作是否真正推进了 **A2A 互操作** 的可验证性。AIP 指出 MCP/A2A 缺少可验证委托链，适合补充 A2A 章节的安全边界。 因此，本章会把论文结论放回不变量、失败窗口和实验断言中，而不是把研究当作参考文献列表。

### Open Problems

1. 如何把 `Agent card` 的正确性拆成可组合的局部不变量，并在不同 Agent runtime 中复用 verifier？
2. 当“把 agent-to-agent 做成普通 chat”与“没有 task id 无法恢复”同时发生时，**A2A Protocol** 与 **Google Agent Development Kit** 的公开抽象分别能保存哪些证据，哪些状态仍需要外部 reconciliation？
3. 如果模型能力显著提高，围绕 `Task` 的哪些 harness 机制仍属于系统必要条件，哪些只是当前模型能力下的临时补丁？
4. 如何构造一个既保护真实业务数据、又能复现“上下文跨 agent 泄漏”的公开 benchmark，使研究结果可以被第三方验证？


### 深度审计与研究证据链：A2A 互操作

本章重新审计后的核心结论是：**A2A 解决 agent-to-agent 消息、任务、artifact 和能力发现，但身份/授权仍需独立设计。** 这句话只有在代码、实验、开源源码和研究证据四个层面同时成立时才有教学价值。仅靠定义或 API 示例无法证明它，因为 Agent Systems 的风险通常发生在模型决策与外部环境之间的缝隙里。

**与本章最相关的近期/基础研究与官方资料：**

- **[MCP 2026-07-28 specification](https://modelcontextprotocol.io/specification/2026-07-28)**：引入 stateless/self-contained request 与更明确的 tools/resources/prompts 边界。
- **[A2A Protocol](https://github.com/a2aproject/A2A)**：把 Agent Card、task、artifact、streaming/push 作为互操作对象。
- **[AIP](https://arxiv.org/abs/2603.24775)**：指出 MCP/A2A 互操作之外仍缺少可验证委托身份链。

这些资料与本章的关系不是“引用背书”，而是帮助读者识别设计边界。A2A spec、a2a-python、MCP+A2A bridge 是本章对照。 读者阅读源码时应主动寻找四个对象：输入如何进入系统、状态在哪里持久化、动作由谁执行、失败后谁负责恢复。

**实验语义边界。** 本章实验验证 A2A 互操作的 workspace、verifier、artifact 或协作状态；证据等级定义与解释规则统一见附录 A，且 `passed=true` 不得跨级推导 containment/recovery。


## 本章总结与进阶实践

### 核心结论

1. 本章不变量是：**agent discovery metadata and task state are untrusted protocol inputs and require validation**；
2. `Agent card` 必须是可观察软件边界，而不是 prompt 约定；
3. `能力声明机器可读` 与 `cancel 语义明确` 之间必须有状态和证据连接；
4. 模型提出动作不等于系统已经执行，更不等于任务成功；
5. 正常路径只能证明功能，故障路径才能暴露恢复语义；
6. 开源实现的核心价值在于理解真实约束，不是复制 API；
7. 性能优化必须与可靠性/安全不变量一起重新验证；
8. 技术边界和未解决问题是高级系统设计的一部分。
